# DAMS computational evidence infrastructure

This infrastructure serves DAMS RQ2 (the cost and capacity conditions of contribution-contingent governance) and RQ3 (the evidence-plane assumptions). It is not a production deployment specification or a claim that synthetic people correspond to blockchain validators. Benchmark results measure the research software, not organizational efficiency.

## Three environments

1. **Organization simulation:** the Python CPU reference model and independent-world experiments. The central/witness/consensus labels select explicit cost, delay and censorship assumptions; they do not launch ledger nodes.
2. **Contract experiment:** `contracts/` compiles and tests an administrator-attested Solidity research prototype in a local EVM. Its gas, storage and security limits belong to that contract/environment, not to Python agent counts or real distributed consensus.
3. **Future DAMS deployment:** independent controllers, quorum thresholds, keys, availability, privacy and network failures would require their own protocol implementation and measurements. No production server, real organization or paid cloud resource has been deployed by these experiments.

## Executable measurements

```sh
python3 research_tools/benchmark.py plan
python3 research_tools/benchmark.py run --output evidence/benchmarks --repeats 3
python3 research_tools/benchmark.py summarize --path evidence/benchmarks/ACTUAL_BATCH
python3 research_tools/benchmark.py cloud-dry-run --scenario batch
uv run --extra analysis python research_tools/performance_figures.py --batch evidence/benchmarks/ACTUAL_BATCH --figures OUTPUT_FIGURES --tables OUTPUT_TABLES.tex --fragment OUTPUT_FIGURES.tex --state final
```

The tool creates unique directories and launches a clean child interpreter for every cold process and independent world. A second single-world measurement creates a complete fresh model in the same interpreter; it is not a cached simulation. “Cold” means process-cold. The OS page cache is not flushed, and no physically cold disk claim is made. The interpreter's resolved executable is recorded; `DAMS_BENCHMARK_PYTHON` explicitly selects a different executable. The actual source hash is pinned in each task and a mismatch before child execution is refused. All normal model paths remain enabled: daily choices, team/ring help, fallible voting, review, settlement, appeals, decay, learning, fatigue, trace and complete final-state output. A shorter horizon or different number of guilds is explicit in the effective configuration rather than a hidden optimization.

Single-world cells are N=120/T=60, 1,000/30, 10,000/30 and 100,000/3; each has three freshly spawned processes and two fresh models per process. Guilds are `max(4, floor(N/100))`, sites `min(8,max(2,floor(N/1000)))`, team size five and one directed ring edge per person. The selected policy is sublinear with the central stylized backend; the same simulation kernel executes the other policy/backend branches, whose additional sorting, queues and delays can change cost. These cells characterize this explicit workload and do not certify every setting at the same N. A 1,000,000/1 attempt is bounded by an external 1 GiB RSS and 120 s watchdog; any stop is retained as incomplete. The 10,000,000/1 request is passed to real configuration validation and refused by the default two-million-event bound before allocating agents. Neither scale receives a completed-world result merely because a request was made.

For strong scaling, the same four independent worlds (N=1,000/T=30) are run using one, two and four concurrent child processes. Weak scaling uses two worlds per worker. Each batch is repeated three times; final-state SHA-256 is compared for each world across worker counts. Process-level parallelism is used only across independent worlds. There is no MPI partition or GPU path. Numerical-library thread counts are explicitly fixed to one even though the reference kernel uses only the standard library. Scheduling/launch/monitor overhead is included in batch wall time. The sum of individual child peak RSS is a conservative allocation bound, not a simultaneously observed aggregate peak.

The raw measurements distinguish initialization, simulation, statistics, plotting, total wall, CPU time, process high-water RSS, emitted work claims, rate, output bytes and disk I/O. Population generation is inside `Model.__init__`; the initialization timer is therefore inclusive of population generation, and a separately timed generation subphase is unavailable rather than invented. The CLI's core-wall snapshot is read before final output hashes and the completed manifest write. Complete wrapper-wall and CPU measurements include those operations and measurement readback; parent spawn-to-exit wall additionally includes startup, collection and monitoring. All three are retained rather than silently relabelling the core timer. The complete-wrapper residual beyond separately timed phases includes provenance, JSON/CSV serialization, output hashing, manifest write, I/O and readback. No compiled kernel is used. Network I/O is zero for this code path, not an observation about unrelated processes on the computer. macOS disk bytes are read from `proc_pid_rusage(RUSAGE_INFO_V2)` using the installed Apple SDK layout; Linux uses `/proc/PID/io`. These kernel-accounted disk bytes differ from logical output size because of caching/writeback. Unsupported measurements are null. CLI OS high-water RSS is read before final output hashes; warm RSS inherits the child's previous high-water and allocator state, so it is not an independently reset per-run high-water. The separate guardian peak samples the entire child, including both complete fresh models and their final hashing, every 50 ms; it supplies a more conservative observation for memory planning, while remaining a sampled rather than continuous peak.

Results are saved as `measurements.csv`, `scale_summary.csv`, `parallel_summary.csv`, `parallel_consistency.json`, raw child manifests/logs and failure/refusal records. Min/max across timing repeats is a hardware-timing range, not a confidence interval over people or a statistical governance effect. Source, configuration and output hashes are authoritative; performance should be repeated after any source change.

The completed current-core batch is `evidence/benchmarks/20261007T143303-cpu-benchmark-6ad2db33c118/`, pinned to full core `3d67a62e6eb2c78b4ac28aec497c7b5e43390d476cb8196309da0a9b9f644b90`. It contains 24 cold/warm complete-world measurements, 78 parallel complete worlds, an actual bounded million-person RSS termination and a ten-million-person event-cap refusal. The earlier `61149d88...` batch is retained as preliminary evidence, with its original manifests and source snapshot, and is excluded from current final cells. The current batch's `measurement-tool.py` is the exact original executing driver, checked against its pinned plan. Later summarizer and figure-generator byte hashes are recorded separately in `publication_artifacts.json`, without rewriting execution provenance. Final publication checks the currently installed full-core hash, scale/parallel CSVs against retained raw JSONs, repetition counts, and per-world hash consistency before generating vector figures and LaTeX. The default `analysis-ready` mode preserves preliminary evidence and writes pending markers rather than asserting a final-version run.

## Resources and stopping

The measured host is Mac14,9 / Apple M2 Pro, arm64, 12 physical and logical CPU cores (eight performance and four efficiency cores), 16 GiB installed RAM, macOS 26.6. The benchmark uses a resolved CPython 3.14.6 executable; actual child manifest versions remain authoritative. APFS is on the local SSD, with about 32 GiB free at final-batch start; the exact byte count and initial/final load averages are retained. User applications and OS services continued, while no other DAMS scientific batch ran during timing. This is shared interactive-host evidence, not an idle-host certification. This host is an observed platform, not the mathematically smallest machine capable of running the code. Linux, Windows/WSL and containers are not thereby certified. The Docker CLI is present, but the daemon cannot be reached; no container execution has been verified.

Ordinary benchmark children use the model's 1.5 GiB sampled high-water limit, at most two million declared work events, 500 MB output limit and 600 s per simulation. An external watchdog samples resident memory every 50 ms and terminates the child above 2 GiB or its complete-process wall budget. The million-agent attempt uses 1 GiB/120 s external bounds. Sampling is not an OS guarantee of zero transient overshoot. A process kill can leave the core manifest at `running`; the separate watchdog record is the authoritative terminal failure evidence, and no complete result is inferred. Previously saved checkpoints remain intact. A newly checkpointed state is not guaranteed on RSS termination. The benchmark's small wall-limit test deliberately fails and retains its real failure/checkpoint rather than suppressing it.

Do not increase N, T, queue backlog, concurrent workers or output retention merely because a smaller case passed. A planning rule is to keep projected concurrent peak RSS below half the installed RAM, retain at least 4 GiB for the OS and interactive work, and retain at least twice the projected final outputs plus 5 GiB free disk. Treat those as conservative operating rules, not validated universal constants. If memory projection exceeds that envelope or a confirmed study cannot finish within its planned overnight window, prefer a workstation/HPC allocation or revise the exact implementation with semantic-differential checks before increasing resource caps. No model module may be silently disabled to meet a resource target.

## Why large N is costly

`Agent` and `Claim` are Python dataclass objects; lists/dicts, daily frozen snapshots, effort/help maps, per-guild heaps, sorted authority/Gini statistics, unique seen-event strings and completed-delay lists all consume memory. Each person emits one claim every day. Agents and sparse links therefore contribute O(N), while retained seen IDs/delays and finite-horizon pending queues can contribute O(NT). Full final-state creation duplicates dataclass dictionaries and materializes JSON strings; peak RSS can occur after the simulation and must include serialization. The CPU reference has approximate O(NT) draws/choices plus claim heap operations and sorting. With G≈N/100, within-guild sort size remains bounded; commit queues, final sorting of seen IDs and growing retained histories need additional logarithmic or output terms. Fixed G and large guilds change this profile.

Use measured per-agent initialization, per-work-claim simulation, per-event retained memory and full-output serialization coefficients to construct **conditional** projections. Compare the N=10,000/T=30 and N=100,000/T=3 cells: both emit 300,000 claims but have different agent/queue/history loads. Do not fit one population-only line to both and call it validated. Timing ranges, model structure and the overlap of measured scales delimit the projection. Million/ten-million projections outside the observed range should use a broad safety envelope and remain unsupported until a bounded exact run or a semantics-preserving optimized implementation passes differential checks. A memory-bounded event ledger, compact arrays and streaming quantiles/hashes are candidate engineering changes; none is claimed implemented merely because it is proposed.

`conditional_projections.json` records the exact nonnegative active-set fit, raw local residuals, inclusive phase-rate ranges, whole-child memory observation and unexecuted 30-day scenarios. `projection_withheld_diagnostics.csv` refits after leaving out each workload cell. Its cross-horizon memory instability shows why a very small four-cell full-fit residual cannot validate the N/NT structure, external capacity or million-person forecasts. The declared 0.5–2 times memory range and factor-two time margin are planning allowances, not empirically established coverage, guaranteed upper bounds or confidence intervals. Default event caps would refuse every projected 100,000/1,000,000/10,000,000-person 30-day request; no such complete world is asserted.

## Cloud dry-run prices and risk

`cloud_costs.json` records prices checked on 2026-10-07 and primary-source links. The `e2-standard-4` on-demand US-central1 rate is USD 0.13402284/VM-hour. Balanced provisioned disk is USD 0.000136986/GiB-hour. Planned outbound USA-to-Asia traffic is conservatively charged at USD 0.12/GiB without relying on the first free GiB. These are region/currency/date-specific estimates, not a purchase quote. [Compute pricing](https://cloud.google.com/products/compute/pricing/general-purpose), [disk pricing](https://cloud.google.com/compute/disks-image-pricing), [network pricing](https://cloud.google.com/vpc/network-pricing).

The executable dry run calculates `VM_rate × (job_hours × 1.2 + idle_hours) + disk_rate × GiB × retention_hours + transfer_rate × egress_GiB`. A quarter-hour single-world reservation plus quarter-hour idle time, 50 GiB retained for 24 h and 2 GiB transferred estimates USD 0.4781. An eight-VM-hour batch plus one idle hour, the same disk for seven days and 20 GiB transferred estimates USD 4.9713. A monthly 120 VM-hour reservation plus ten idle hours, 730 h disk retention and 100 GiB egress estimates USD 37.6395. VM-hours are reserved planning assumptions, not runtimes extrapolated from an Apple CPU. Costs include 20% compute retry allowance; interruption can still exceed it. A checkpoint helps only if persisted before interruption. Taxes, external IP/NAT, premium operating-system licences and unspecified managed services are excluded and must be added if provisioning introduces them.

The dry run rejects plans above USD 1/10/50 single/batch/monthly budgets or 1/12/160 VM-hour planning maxima. These checks do not configure billing alerts or stop an actual VM. Provisioning, scheduler stop rules, durable checkpoint storage and spend enforcement would have to be established under a separate authorization; no cloud resources or purchases have been initiated. The available local workstation is the first choice for bounded method exploration. HPC/cloud is justified by a measured memory or completion-window constraint, not by N alone or by a presumption that DAMS needs a GPU.
