# Controlled GCP research execution

The cloud path runs the same `dams_sim pipeline` used locally. It evaluates DAMS governance mechanisms; VM throughput is a research-software measurement, not an organizational benefit. No GPU, Local SSD, bare-metal variant, Tier_1 network or managed cluster is requested by this controller.

## Shared entry and installation

```sh
./run.sh --spec validation --scale 120
./run.sh --spec governance-scale --scale 1000
./run.sh --spec scale-confirmation --scale 100000
```

The default is bounded local validation at 120 people. The spec selects a versioned scientific protocol, and scale is its population. The shared scheduler verifies source/configuration, executes independent cases within CPU/RAM/disk/event/time limits, resumes matching cases, and generates analysis and the report. Unsupported settings fail; no module or sample is silently removed. `historical-full-study` preserves the published small-population protocol.

For a source installation, the release maintainer publishes the actual immutable SHA in this template:

```sh
curl --fail --location --proto '=https' https://raw.githubusercontent.com/rui-h-a/dams-simulation/RELEASE_SHA/bootstrap.sh | bash -s -- --commit RELEASE_SHA --spec validation --scale 120
```

`RELEASE_SHA` must be replaced with an actually published 40-character commit containing this entry. This template is not a claim that a new release has been published. `bootstrap.sh` fetches only that commit from the public repository, checks the resolved SHA and refuses modified or untracked existing source; gitignored runtime results remain reusable. The minimal prerequisites are a POSIX Bash terminal, git, curl, tar and SHA-256 tooling, network access to the official source/registries, and a user-writable filesystem. Native Windows requires WSL2; arbitrary platforms are not promised.

`run.sh` uses the verified `uv 0.9.26` version, installs its official release binary with a pinned SHA when absent/different, and prepares managed Python 3.14.2 and `uv.lock` without sudo or shell-profile changes. Existing external tools remain external trust prerequisites; their actual version/path is printed. First-install network needs differ from a prepared runtime. `--prepare-only` performs installation and doctor without starting a study. Actual missing-uv installation and doctor have passed on macOS arm64. Linux installation, systemd and cloud recovery remain unverified until their real execution records exist.

## Private authorization and state

Ordinary public use does not authorize spending. An authorized coordinator supplies a mode-0600 JSON configuration outside the public tree and sets `DAMS_CLOUD_PRIVATE_CONFIG` and `DAMS_CLOUD_STATE_DIR`. These advanced settings are not choices the ordinary user must hand-configure. The selected spec/scale must match the frozen task in that configuration. There is no automatic on-demand fallback.

The private schema version is 1. Required fields are `authorization_id`, `project`, `dedicated_project=true`, `region`, `zones`, `bucket`, `service_account`, `subnet`, immutable `image` selfLink and `image_id`, `source_commit`, `global_deadline_utc`, cumulative `budget_cap_usd`, `reserve_usd`, `prior_spend_usd`, `price_snapshot`, ordered `stages`, `gcloud_configuration`, `gcloud_account` and `network_mode`. Each stage has an immutable ID, machine type, complete scientific spec/scale, maximum seconds including startup and persistence, disk GiB, result/egress bounds, operation/noncompute reservations, and versioned `runtime_limits`. Credentials, billing identity and monetary limits never enter the VM or public scientific metadata.

`execution_stage_ids` selects an ordered subset of the fully priced plan for the present invocation. Thus the small Linux validation can run while large quotas remain pending, without resetting the authorization or spending its protected future-stage allowance. Earlier stages must be scientifically verified before a later one starts. The execution receipt distinguishes selected stages from pending research work. The public test fixture in `tests/test_cloud_control.py` is a minimal fictional schema example, not a user budget or launch configuration.

The POSIX coordinator and ledger use process locks plus atomic, fsynced writes. A reservation exists before any paid object upload or VM request. It includes all stages, outstanding allocations, prior consumption and cleanup margin; a later stage cannot consume the amount reserved for the highest target. Budget, authorization and global deadline cannot reset across retries, dates, sessions or coordinators. Settling an absent VM charges the full conservative reservation; optimistic billing-delay refunds are not used. The scientific scheduler's task deadline is earlier than guest shutdown and Compute Engine deletion, leaving a persistence interval.

The source commit, complete future stage plan and cloud resource identities are also frozen in the ledger. Only the ordered execution subset and checked rate refresh can change; a new study design or source cannot silently reuse that authorization. Failed science remains unsettled. All-stage costs include a separate bounded fixed-source package allowance as well as result storage.

## C4D prerequisites and costs

C4D highmem targets are 96/192/384 vCPUs and 756/1,512/3,024 GiB according to the machine catalog. vCPUs are threads, with two threads per physical core. The 384 VM exposes two vNUMA domains. C4D uses Hyperdisk and gVNIC; the implementation explicitly requests ordinary Hyperdisk Balanced baseline 3,000 IOPS/140 MiB/s, not capacity-derived performance defaults. Catalog entries do not establish instantaneous capacity or guest-visible RAM. [Machine specifications](https://docs.cloud.google.com/compute/docs/general-purpose-machines), [Hyperdisk baseline and limits](https://docs.cloud.google.com/compute/docs/disks/hd-types/hyperdisk-balanced).

`cloud_prices.py` parses retained official Billing Catalog records by exact description, region, currency, effective time, usage category and zero-start tier. `CLOUD_PRICE_SNAPSHOT.json` retains selected SKUs, acquisition/source hashes, raw units and both RAM interpretations. Official pricing calls machine memory GB a binary GiB; the raw C4D RAM SKU names `GBy.h` with a decimal byte conversion. Planning takes the maximum of nominal binary-memory arithmetic and the catalog byte-quantity arithmetic, with an additional private margin. Monthly disk API conversion and conservative 730-hour planning conversion are separate. These are dated planning rates, not an invoice quote. Refresh before creation; Spot prices and availability may change. [Compute billing units](https://cloud.google.com/products/compute/pricing), [Catalog API](https://docs.cloud.google.com/billing/v1/how-tos/catalog-api), [Disk rates](https://cloud.google.com/compute/disks-image-pricing).

Reservations include CPU/RAM, provisioned disk, Standard object storage, immutable checkpoint generations, request operations, downloads, retries, idle startup and any explicitly introduced IP/NAT/logging costs. No free tier, promotional balance, discount or tax exemption increases authorization. GCS charges retained versions and soft-deleted objects too; copying between regions and downloading to the Internet have different rates. The controller meters cumulative download bytes. [Storage pricing](https://cloud.google.com/storage/pricing).

Before each paid stage, the controller checks its **granted** regional Spot CPU pool and global CPU headroom. Once preemptible quota has been requested, applicable Spot resources consume only that separate pool; the standard C4D-family quota is neither an additional requirement nor a depleted-Spot fallback. A pending request is not a grant. Candidate zones must be in the same explicitly priced region. The coordinator must also verify disk/IP quotas, organization policies and service-account permissions. [Applicable quota pools](https://docs.cloud.google.com/compute/resource-usage).

The `iap-ephemeral-ip` mode uses IAP-only SSH management, HTTPS-only egress, and an ephemeral Spot IPv4 address reserved at the dated published rate. Preflight reads actual project labels, image ID/architecture, subnet/private-Google-access and applicable firewall rules; a coordinator boolean alone does not pass these checks. Allow rules must target the restricted service account and precede explicit deny-all rules. `internal-offline` additionally requires an executed image/lock-bound offline doctor receipt and uses offline dependency preparation. The small real guest must still establish outbound operation and applicable organization-policy behavior before scaling. Every SDK call specifies the private named configuration/account, project and applicable zone. [IPv4 rates](https://cloud.google.com/vpc/network-pricing).

## Lifecycle, failures and recovery

Only one task VM is allowed at once. Deterministic names and task/stage/source labels bind inventory to a frozen intent. Before reuse, the controller verifies machine, Spot provisioning and absolute deletion time. A create timeout does not mean failure: the ledger becomes uncertain and no duplicate create is issued. Reconnection requires a matching VM or completed Compute operations plus confirmed VM/disk absence. Capacity retries are bounded, use the same reservation/deadline, and stop before the budget or cleanup interval expires. Logs append unique command records instead of overwriting prior attempts.

Each VM is created with absolute `--termination-time`, Spot and `--instance-termination-action=DELETE`. `cloud/install-services.sh` installs an independent systemd pipeline, periodic persistence timer and deadline watchdog. The work does not depend on an interactive SSH session. Reboot/reconnection cannot create a new case roster. Shutdown persistence is a last attempt; preemption may leave only the preceding verified checkpoint. [Automatic termination](https://docs.cloud.google.com/sdk/gcloud/reference/compute/instances/create), [Spot behavior](https://docs.cloud.google.com/compute/docs/instances/create-use-spot).

Guest authentication uses the attached, restricted service account. No user gcloud login, ADC, long-term account key or private Git credential is packaged. The clean source tar uses an allowlist, pins a full commit and verifies every source byte against its manifest. The guest verifies the package and file map before launching the same entry.

Completed outputs and two-generation checkpoint indexes are copied consistently, SHA-256 addressed, uploaded under conditional immutable keys, then downloaded and hashed to verify the actual remote bytes. A snapshot descriptor is published only after its file inventory and checkpoint/index pairs match. A mutable latest pointer is not proof of a complete study. Upload state survives a guest replacement; its cumulative immutable bytes cannot exceed the storage reservation. Retained remote history is conservatively bounded, rather than silently deleted to disguise its cost. Final terminal markers identify the actual instance and source; disappearance or a smoke run cannot certify a formal cloud stage.

Restore and periodic upload share an exclusive tree lock. Restoration is staged outside the visible output tree and published atomically; empty trees and partial download files cannot replace the latest snapshot. Storage accounting includes immutable blobs, snapshot descriptors, mutable pointers, terminal metadata and the self-sized upload ledger. A replacement guest inventories retained objects to account for ambiguous uploads absent from the preceding ledger. The controller verifies the final snapshot identity and deletes compute before a potentially large raw-data download, then requires full byte and scientific validation before settlement.

Local tests cover budget/deadline immutability, forbidden escalation after failure, quota-pool selection, ambiguous creation, actual-response validation fixtures, named SDK identities, source packaging, partial upload, checksum corruption, paired checkpoints, output caps and controlled CLI refusal. A genuine small Model subprocess was SIGKILLed between completed days; its checkpoint snapshot was downloaded from a local store substitute, restored and compared byte-for-byte with uninterrupted final state. This does not certify GCS/IAM, a real Spot interruption, Linux/systemd or expensive-stage performance. Restored trees preserve unlisted old files in a separate history directory. Complete stage acceptance also requires the shared independent specification/inventory/child-origin/publication validator, including actual requested machine provenance.

JSON-API HTTP requests and cumulative coordinator download bytes have durable limits. Request allowances reserve every HTTP attempt at the higher Class A rate, split across the bounded guest attempts and coordinator, plus an SDK source-staging margin. The SDK's internal requests are not individually metered; source staging itself has finite attempts and is not repeated after a successful response. Remote history retains all bounded content-addressed generations, while each local case checkpoint index retains two. The upload timer permits large snapshots to run up to the independently enforced absolute expiry. Guest records include lscpu thread/core/socket/NUMA topology, affinity, memory, block-device settings, and before/after CPU/disk counters; these observations do not establish NUMA optimization.

## Complete closeout

The guest can save outputs and power off; it cannot unlink billing or delete the project. An explicitly authorized coordinator performs `cloud_cleanup.py` after two distinct complete archives pass actual file SHA checks. Closeout records instances, disks, snapshots, custom images, IPs, routers, firewall/subnet/network resources, schedules, storage policies/live versions/soft-deleted objects and log retention. A failed inventory stays unverified, never empty.

The archive receipt must enumerate every regular file in both copies and declare `pipeline_roots` with each required stage ID and relative path. Both complete scientific pipelines are independently revalidated against the frozen private stage plan and expected cloud origins. Two arbitrary matching notes or a selected subset of outputs cannot authorize final project deletion.

Failed, deadline-limited or quota-blocked work has a separate explicitly authorized `closure_mode=abort` path. It still checks two exhaustive file/byte inventories and binds their `cloud_object_files` map to every actual retained object generation through the provider roster, size and MD5, in addition to local SHA-256. It reports `science_complete=false` and preserves incomplete-stage evidence; unavailable future results do not trap paid resources. Abort closure does not certify the thesis goal or a complete study. Only the private coordinator can authorize this path.

Final closeout uses the same private state directory and coordinator lock as execution. An executed closeout writes a durable task fence that prevents subsequent launches. VM and disk absence must be positively observed before the final retained-object roster is checked: the coordinator first quiesces the guest, preserves its final uploads and disk evidence, and rebuilds the two archives. Closeout refuses an active or unverified writer instead of deleting it after archival verification. Both complete and abort receipts map every retained object generation. Deletion addresses only those verified generations and an empty bucket, never a recursive wildcard. A final provider check rejects any new unarchived generation before billing unlink or project shutdown. Authorization flags require JSON `true`; strings and numbers are refused.

Project shutdown additionally requires confirmed bucket absence, sealing even a previously started resumable upload. An unknown deletion response is reconciled on reconnect; an existing bucket remains open closeout work, even if its current objects were archived. A matching task fence permits previously deleted archived generations to be absent during reconnect, while every newly observed generation still requires both archives. Storage cleanup margin remains reserved during this reconciliation.

After verified archives, explicit project-scoped deletion commands cover observed VM/disks/snapshots/custom images/IP/network/schedule resources and live/noncurrent bucket contents. The coordinator records deletion responses and post-deletion inventories. Existing soft-deleted generations retain their original provider policy and are not falsely declared purged. Final actions detach project billing and request project shutdown, then check `billingEnabled=false`, no linked billing account and `DELETE_REQUESTED`. Cleanup remains callable after the scientific/global creation deadline; it never opens a new compute allowance. It never closes the shared billing account or touches another project. Provider shutdown is recoverable and is not immediate physical erasure; prior accrued charges can settle later. Unconfirmed deletions/inventories remain visible even when billing is disabled. Operational evidence and the ledger remain in the private archive. [Project billing control](https://cloud.google.com/billing/docs/how-to/modify-project), [Project deletion](https://docs.cloud.google.com/resource-manager/docs/project-deletion).

At this revision, no real VM deployment, Spot recovery or final project closeout is claimed by this document. Update the support matrix only after actual recorded execution, not from a generated script or dry run.
